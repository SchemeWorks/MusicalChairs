# Native Solana — M7 contract supplement (2026-10-14)

Scope: the three items from Codex's independent M7 static review at `8fdade5`, plus Codex's targeted review of `366df88` (IMPL-45) and the M7 findings. Item 1 is a wording clarification of the plan; items 2 and 3 record the bounded program corrections (kanban IMPL-42, IMPL-43, IMPL-45); item 3's deferred-refund reading is **accepted by Codex in principle with the IMPL-45 narrowing**; items 4 and 5 document M7-F1 and M7-F4. Nothing here reopens the accepted architecture (D1–D9), the decision register or the economics; no custody or admin override, no new fee, no population cap. Local work only.

## 1. Canonical candidate digest (clarifies plan M7 step 1, L583)

The plan's test sketch says the sealed digest "equals SHA-256 over the ordered pubkeys". The implemented and canonical digest (`solana/programs/musical_chairs/src/sampling.rs`, `candidate_digest_start` / `candidate_digest_next`) is a **chain over (owner, loss) in participant order**:

```
D_0     = SHA256("MC/EEC/CANDIDATES/v1" || set_tag_u8)
D_{i+1} = SHA256(D_i || owner_i (32 bytes) || loss_i (u128, little-endian, 16 bytes))
```

The sealed digest of the selected set is `D_n`; it is the `sealed_digest_32` input of the protocol seed (spec §4) and is pinned by `solana/fixtures/sampling.json`. Binding each candidate's loss figure into the chain is deliberate: the sealed set then commits to the amounts the promotion entitlement is computed from, not only to the identities. The plan wording "ordered pubkeys" is superseded by this definition; no behaviour changes.

## 2. `deadline_seconds` is frozen at 600 s (IMPL-42)

Spec §4 (L220): `promotion_deadline = close_started_at + 600`, pinned once at the closing payout, never reset. The closing payout copies `ConfigVersion.deadline_seconds` verbatim, so before IMPL-42 a staged value of 1 would have re-timed every close to a one-second window. `ConfigTerms::validate` now requires `deadline_seconds == PROMOTION_DEADLINE_SECS` (600; `state.rs`) and rejects anything else with `InvalidState`, fee-only, like the quota and the five fixed-helper pins before it.

Evidence (receipt `docs/solana/evidence/2026-10-14-m7-deadline-pin.json`): unit cases 599 and 601 RED on the old validator ("validator accepted the terms") → GREEN; harness staging variants `noncanonical_deadline_short` / `_long` (G-signed through the Squads stand-in) RED on the old ELF `27de0cfc…` (staging accepted) → GREEN on the patched ELF; the positions suite's closing row asserts `promotion_deadline == close_started_at + 600` exactly.

## 3. Undeliverable owner refunds are deferred, never forfeited (IMPL-43, narrowed by IMPL-45) — accepted by Codex in principle with the IMPL-45 correction

### The defect

`close::settle_books` (settlement at terminal promotion), `book_return` and `withdraw_provider_return` treated an owner remainder that the runtime could not deliver to the immutable `owner_refund_destination` as forfeited: the lamports were moved into `ops.unallocated_excess` and the owner liability zeroed. Trigger: a zero-pot (net-0) closing payout to a fresh destination with an owner reserve contribution below the rent-exempt minimum, or a destination that fails `validate_destination`. This violates spec §8.5 ("`locked_owner_remaining` is transferred … to the recorded owner destination") and DR-14's owner-attributed return. Captured RED (`2026-10-14-m7-owner-refund.json`): after `expire_promotion` the owner's 500,000 lamports were neither paid nor owed ("owed 0, paid 0").

### The runtime rule, and what the local runtime can prove

Agave's rent-state rule (`svm/src/rent_calculator.rs`, copied verbatim into LiteSVM 0.7.1 `src/utils/rent.rs::transition_allowed`, commit `6fbbaf67`): a writable account may end a transaction rent-paying (0 < lamports < minimum) only if it was rent-paying before, kept its data size and was **not credited**. For a data-less destination holding `c` lamports, a credit of `a > 0` therefore succeeds iff `c + a >= minimum(0)`. The old predicate `c > 0 || a >= minimum` wrongly called a legacy rent-paying destination deliverable; on the cluster that transfer fails and, because settlement runs inside `expire_promotion` / `apply_promotion` / `build_candidates`, it would have blocked round recovery.

LiteSVM 0.7.1 applies the check only to accounts **with data** (`check_accounts_rent` skips `account.data().is_empty()`), so system wallets are never checked locally: `tests/transfer_constraints.rs` shows every probe succeeding in LiteSVM although the cluster rejects three of them. The predicate is therefore validated against the rule text (restated in the test and compared on a dense grid), not against local execution. This limit is recorded in the receipt and in the test's module docs; a LiteSVM upgrade that closes the gap flips the pinning test.

### The correction (smallest contract-preserving change)

1. `credit_is_deliverable(c, a, min) := c + a >= min` (saturating). Conservative under the rule: when it is false the credit is deferred, never attempted.
2. `settle_books`: the sponsor remainder returns to `free_balance` as before; the owner remainder is **paid when deliverable, otherwise it stays in `CloseRecord.locked_owner_remaining`** (held in OpsCash, still counted in `ops.locked_remaining_total`). `reserve_settled` is set either way, so `finalize_round` and every claim path proceed. Nothing is ever added to `unallocated_excess` from owner lamports.
3. `withdraw_provider_return` **preflights before the ORAO CPI** (IMPL-45, Codex review of `366df88`): the owner share `w = min(amount, owner_request_rent_refundable_remaining)` must be zero or deliverable to the bound destination right now; otherwise the call is refused fee-only (`RefundNotDeliverable`) with the Client, the request account and the eligibility / owner-refundable counters untouched, so the same return can be retried once the destination can receive the credit. `book_return` therefore always pays the owner share; a provider return is **never** re-locked into the spendable owner partition (the IMPL-43 version did that before settlement, where `book_locked_rent` could have spent it on B or registry rent — a DR-14 violation Codex caught). The observation and the owner's eligibility stay protected provider-side until an actual atomic owner-paying return.
4. New permissionless instruction `deliver_owner_refund()` (accounts: `close_record`, `ops`, `ops_cash`, `owner_refund`, `system_program`; event-CPI): requires `reserve_settled`; pays the whole `locked_owner_remaining` to the **same immutable destination** once `credit_is_deliverable` holds; `RefundNotDeliverable` (6051, fee-only) while it does not; `NothingDeferred` (6050) on replay or when nothing is owed; `WrongAccount` for any other destination. Emits `OwnerRefundDelivered { round_id, close_id, amount, destination }` (event 20 of the frozen schema; fixture regenerated).

Accounting: the OpsCash identity `lamports − protected_rent == free + L + unallocated_excess` is unchanged (the deferred lamports are inside `L`). The invariant "`reserve_settled ∧ locked_owner_remaining > 0` ⇔ a deferred owner refund is owed" is the single source of truth; delivery zeroes it exactly once; the only way lamports enter that state is terminal settlement of the close's own owner partition. Conservation-table rows (spec §8.6) affected: settlement gains an *undeliverable* variant (OpsCash 0, free +s, s → 0, o unchanged, L −s); a new row `deliver_owner_refund` (OpsCash −o, L −o, o → 0); `withdraw_provider_return` with an undeliverable owner share is **not a row** — it is refused before anything moves (OpsCash 0, free 0, o 0, L 0, counters unchanged).

What it is not: no admin or sponsor can redirect, sweep or spend a deferred refund (the destination is immutable and the partition is excluded from `free_balance`); no fee; no change to admission, payouts, allocation or the promotion economics. Limit: if the destination becomes permanently unable to receive lamports (for example, assigned to another program by its own authority), the refund stays locked to the owner indefinitely. That is the price of destination immutability, which the accepted contract requires; the alternative (any redirect authority) is exactly what Codex excluded.

Evidence (`2026-10-14-m7-owner-refund.json`): RED on the IMPL-32 ELF; unit tests inverted RED → GREEN (settlement, delivery, predicate table); LiteSVM rows `fresh_destination` (deferred → `RefundNotDeliverable` → funded → delivered once → `NothingDeferred`; wrong destination `WrongAccount`), `legacy_rent_paying_destination` (expiry not blocked, deferred, delivered), `deliverable_destination` (paid at settlement, nothing deferred), `pending_close` (`InvalidState`), `deferred_after_finalize` (finalization carries the seed and reopens the round with the refund still owed; delivery afterwards); IMPL-45 row `undeliverable_owner_share_is_refused_before_the_cpi_and_retried_once_the_destination_is_funded` in the close suite (Pending close, fulfilled and observed request, owner-positive refund, fresh destination: refused before the ORAO CPI with Client / request / counters byte-identical, expiry and finalization unaffected, funded-destination retry pays the owner exactly once) RED on the IMPL-43 ELF, GREEN after; every row asserts fee-only rollback on rejection and the OpsCash identity after each step.

Codex position (targeted review of `366df88`): the terminal reserve deferral in the permanent `CloseRecord` and the permissionless immutable-destination `deliver_owner_refund` are sound and accepted in principle (no redirect or admin authority, no recovery blockage); the reuse of the settled owner partition is accepted with the IMPL-45 correction; spendable provider refunds are not. No dedicated field is needed.

## 4. M7-F1: a pre-funded request PDA blocks that close's draw (documented, no redesign)

The ORAO request address is a PDA of public inputs once the candidate set is sealed, and the captured ORAO executable creates it with `create_account`, which refuses an address that already holds lamports (system `Custom(0)`); `request_round_draw` then fails closed, as the frozen contract requires (`Collision`, no alternate seed, no reroll). Anyone can therefore pre-fund the address and force that close's promotion to expire `Skipped(Deadline)`. Measured locally (close-suite row `collision_with_preexisting_request_fails_closed_no_alternate_seed.prefunded_system_account`): the request fails before any fee or rent moves; expiry, settlement, finalization and claims all complete; the seed carries to the next round. Cost to the griefer per close: the rent-exempt minimum of an empty account (890,880 lamports ≈ 0.00089 SOL at the default rent schedule, which LiteSVM and the cluster share for data-less accounts) plus a transaction fee, and the lamports are stranded at the PDA. Impact: one skipped Series B promotion (a bonus draw, never owed cash); no lamports are lost by the project or the participants. Codex: this fits the frozen contract; recorded here as an accepted griefing risk with its cost; no seed or provider redesign and no new gate.

## 5. Plan wording corrections (M7-F4)

The provider fee moves at **request** time, not at fulfilment: `request_round_draw` pays Client → request account (+rent) and Client → Treasury (+fee); fulfilment only returns the request account's excess rent to the Client. The plan sketch "Treasury +300,000 at fulfillment" is superseded by the probe receipts and the close-suite rows (`request_decrements_remaining_partitions_sponsor_first_and_records_spent_split`, `fulfillment_reimburses_excess_rent_to_client_only_and_changes_no_ops_accounting`). M7-F2 (a late capture on an already-terminal close records `IgnoredLate` before the terminal check; cosmetic) is deferred to the M8 program pass; M7-F3 (frozen codes 6027/6047 never raised) stays reserved.
