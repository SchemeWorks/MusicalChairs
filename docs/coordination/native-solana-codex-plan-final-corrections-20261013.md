## F1 — Authenticate provider returns and debit refundable balances (accepted C2)

Spec L302, L392, L398–412; DR-32 L177. Current `record_provider_return` accepts physical surplus or reclassifies anonymous `unallocated_excess`, but never verifies the advertised ORAO withdrawal. G can classify a plain donation as a provider return, contrary to accepted no-excess-credit policy. Also `owner_request_rent_refundable` is never decremented, so two partial returns can pay the same owner share twice.

Use an atomic G-authorized provider withdrawal wrapper (rename existing instruction if helpful): pinned ORAO Client/withdraw CPI, validated G Vault signer and tuple, explicit destination OpsCash, before/after physical Client/OpsCash balance deltas, then accounting/refund in the same instruction. Verify the pinned adapter's withdraw CPI details as an implementation obligation; never infer an inner sibling instruction from G signature alone. No anonymous-surplus reclassification. Limit attributed returns by each close's independently authenticated fulfilled-request rent reimbursement minus already returned amount (not full pending rent, retained fulfilled-request rent, observed Client gifts or another close's entitlement). Observe fulfilled/late fulfilled request by its retained binding, once, before adding to a stored aggregate eligible-return counter; no unbounded scan over historical closes. A still-pending request has no fulfilled reimbursement to return.

Compute `owner_share = min(amount, owner_request_rent_refundable_remaining)`; decrement that remaining field by `owner_share` and the eligible remaining budget by `amount`, update the close/global returned counters, pay only the immutable owner destination; sponsor share to free Ops. Define the retained request-rent source attribution explicitly (including who bears retained rent and priority on the real reimbursed amount); no refund beyond actual authenticated reimbursement. Anonymous Client credits are observations and may physically back a withdrawal but never create new eligible per-close reimbursement. Provider deficits are informational: specify a checked equation using **known eligible unreturned reimbursements** versus Client spendable observed balance above protected Client rent; pending/retained request rent is separate. A later real return updates the aggregate/counters; no deficit turns into a game debt or blocks reset/claims. If wrapper cannot execute with pinned SDK, report exact source constraint; no silent alternate custody override.

`Ops.locked_remaining_total` is a maintained O(1) aggregate, not an unbounded sum at runtime: add on accepted reserve/budget increase; subtract exactly on every spend and terminal settlement; correct stale `locked_total` references. State the OpsCash identity after actual owner payouts in the transition table (currently shows zero despite transfer). Tests: two partial provider returns then replay; exact owner residual; pending vs fulfilled vs late refund; G signer without withdrawal cannot credit; anonymous OpsCash donation never reclassified; wrong client/destination; CPI failure rollback; two closes cannot claim the same refund; aggregate lock/eligible-return invariants; observed deficit and later return.
