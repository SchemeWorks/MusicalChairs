## Findings

### SEC-1 (Medium, confidence High): staged config can carry a Simple toll table that every affected payout refuses

- Location: `controls.rs:113-188` (`ConfigTerms::validate`) vs `positions.rs:880-892` (`simple_toll`) and `positions.rs:923-929` (`simple_settlement`).
- Root cause: `validate` pins five fixed-helper values (`plan_rates_bps_per_day[0]`, A/B entitlement, `seed_bps`, `open_cutoff`, controls.rs:170-177) because "anything else would be accepted at staging and then ignored or unusable". It does not pin `simple_toll_bps` or `simple_toll_day_bounds`; it only checks each bps <= 10,000 (L115-129) and `bounds[0] < bounds[1]` (L182-185). But `simple_toll` computes the tier from the config table and then `require!(tier == host, InvalidState)` against the hard-coded economics table (`fees::simple_toll_bps`: 1,200 under 7 days, 750 under 14, 300 after). Any config whose table differs at the elapsed time of a withdrawal makes `withdraw_simple` revert with 6001.
- Failure path: G stages v2 with a plausible retune such as `simple_toll_bps = [1200, 750, 250]` (or bounds `[6, 14]`, or `[7, 15]`). `validate` passes, `stage_config_version` and `activate_config_version` succeed (`controls.rs:612-697`). Every Simple position opened under v2 then fails `withdraw_simple` (`positions.rs:1445-1458`, error from `simple_settlement`) for the whole mismatched window. For the late tier that window starts at day 14 and runs to expiry at day 21 and beyond; `close_simple_position` cannot help (needs `owed == 0`, positions.rs:1492). Positions are pinned to their config (positions.rs:690), so staging a corrected v3 does not rescue them; they stay stuck until the round ends, after which they are terminal (`PositionRoundClosed`, positions.rs:843).
- Impact: user earnings unpayable for positions pinned to the bad config. Funds are not stolen (fail-closed), but accrued interest is effectively forfeited if the round ends first. Reachable only by a G-signed stage (2-of-3, 48 h delay, at least one round of lead time), so this is a mis-parameterisation hazard, not an exploit; it is the same class the Codex M5/M6 follow-up already closed for five other fields.
- Evidence it is unguarded: unit test `pinned_config_must_agree_with_the_hard_coded_simple_tables` (positions.rs:1774-1787) proves the payout-time refusal; `config_terms_reject_each_bound_once` (program `controls.rs:2141-2181`) and the M3 row variants (`controls.m3.stage_config_requires_g_and_future_round.noncanonical_*`: quota_count, quota_window, simple_rate, a/b entitlement, seed_half, open_cutoff, deadline_short/long) contain no toll-table case. The record `docs/solana/evidence/2026-10-14-m5-config-pins.json` states toll tiers "remain configurable because the handlers read them", which is not accurate: the handler reads them and then demands equality.
- Minimal fix preserving the frozen contract (no schema, IDL, or error-code change): in `ConfigTerms::validate` add `self.simple_toll_bps == [1_200, 750, 300] && self.simple_toll_day_bounds == [7, 14]` (restate-only, `InvalidState`), or drop the equality in `simple_toll` and make the config authoritative. The first is smaller and matches the existing pattern.
- Required test (RED today): extend M3 row `stage_config_requires_g_and_future_round` (harness `solana/tests/financial-runtime/src/controls.rs`: `terms(effective_round_id)` at L702, `stage_ix` at L660, `Rig::via_g`, `rejected_program`) with variants `noncanonical_simple_toll_early` (`simple_toll_bps[0]=1_100`), `_mid`, `_late` (`[2]=250`), `noncanonical_toll_bound_early` (`[6,14]`), `noncanonical_toll_bound_mid` (`[7,15]`); each expects `ErrorCode::InvalidState` (6001) with fee-only rollback. Add the same five to the `config_terms_reject_each_bound_once` array.

### SEC-2 (Medium if the upgrade authority is ever revoked; Low while G holds it; confidence High on the code path): G-stageable economics are not bounded where the handlers read them

- Location: `controls.rs:113-188` (validate), consumers `positions.rs:672-673` (maturity from `plan_durations_s`), `positions.rs:905-912` (`compound_owed` from `compound_factors_q18`), `positions.rs:497-507` (front-end load), `positions.rs:934` (`jackpot_bps`), `controls.rs:627-634` (`effective_round_id`).
- Root cause: validate requires only `> 0` for durations and `min_game`/`min_a`, `<= 10_000` for load/jackpot/toll bps, and nothing for `compound_factors_q18` or the upper bound of `effective_round_id`.
- Failure paths (each needs one G-signed stage, the 48 h Squads delay, and the round boundary; users bind consent through `open_position(expected_config)`, positions.rs:459-462):
  1. `plan_durations_s[1] = 1` with the default 4.47x factor: a Compound15 position matures in one second and `settle_compounding` pays `min(principal*4.47, pot)`. A colluding Sybil position can drain the round's pot (all other users' deposits). Same with a Simple duration of `u32::MAX` seconds (11%/day accrual for 136 years) or a huge factor.
  2. `front_end_load_bps = 10_000`: every new deposit becomes `management` (`entry_split`), withdrawable by the G-chosen `management_recipient` via `withdraw_management`.
  3. `min_game`/`min_a` = `u64::MAX`: deposits impossible (griefing).
  4. `effective_round_id = u64::MAX`: the staged version can never activate, and `stage_config_version` only accepts `active+1` (controls.rs:623-626) and cannot replace an existing account (6006), so config staging is deadlocked until a program upgrade.
- Impact: today (upgrade authority == G vault; `validate_program_binding`, controls.rs:1448-1464 requires it at initialize) G can already replace the program, so this adds no power. If the upgrade authority is later revoked or blackholed, config staging becomes the only remaining admin path that moves user value. This is the same "admin methods survive the freeze" lesson recorded for the ICP canisters.
- Minimal fix: decide the envelope before any revoke. Options without a schema change: restate-only pins like the existing five for `plan_durations_s` (1,814,400 / 1,296,000 / 2,592,000) and `compound_factors_q18` (the `ROI_15_Q18`/`ROI_30_Q18` constants in `economics/src/earnings.rs`), a cap on `front_end_load_bps` and `jackpot_bps` (owner picks, e.g. <= 1,000 and <= 2,500), an upper bound on `effective_round_id` (e.g. `round_id + K`), and a ceiling on `min_game`/`min_a`. If configurability is intended, document that G trust includes these parameters and that the UI must render the staged terms before `effective_round_id`.
- Required tests: M3 `stage_config_requires_g_and_future_round` variants `noncanonical_compound15_duration`, `noncanonical_compound30_duration`, `noncanonical_simple_duration`, `noncanonical_compound_factor_15/30`, `front_end_load_above_cap`, `jackpot_above_cap`, `min_game_above_cap` (each 6001, fee-only) and `effective_round_beyond_horizon` (6030 `ConfigNotActivatable` or 6001, owner choice).

### SEC-3 (Medium for availability, confidence Medium): dust tolls re-occupy the singleton allocation ticket at ~42:1 keeper-cost amplification

- Location: `positions.rs:984-992` (`toll_route`: any `toll > 0` with `registry_len > 0` routes to `Ticket`), `positions.rs:842-848` (`payout_gate`: `active_ticket == 0`), `positions.rs:468-482` (`series_a_gate`), `controls.rs:683-685` (activation), `positions.rs:1002-1004` (`inline_offered`, only `registry_len <= 8`).
- Root cause: every non-closing payout whose toll rounds to at least 1 lamport starts a full six-phase ticket, and while a ticket is active no other payout, Series A funding or config activation can run. There is no minimum toll, no payer-borne cost, and no cooldown. The attacker's cost is one payout transaction; the work is done by keepers (or other users) in about 6 x ceil(N/8) transactions (measured: 42 transactions per ticket at N=100, rows=8, `docs/solana/measurements-2026-10.md` section 6).
- Failure path: attacker holds a Simple position (0.01 SOL accrues about 12 lamports/s, so a 12% toll is at least 1 lamport after about 1 s). After each ticket reaches `COMMIT`, attacker submits `[commit_ticket, withdraw_simple]` in one transaction (both permissionless/owner-signed; the commit is atomic with the new ticket start, `payout_preflight` needs `ticket.phase == IDLE` which holds after the commit instruction in the same transaction). The ticket is never idle at a transaction boundary, so any other user's payout or Series A funding sees `AllocationPending` (6010). Honest users can only win the handoff by doing the same bundle with a higher priority fee. The inline path (registries of at most 8) does not stop this: it is opt-in by the payer (`inline_offered`, positions.rs:1002-1004), so an attacker simply omits the remaining accounts and starts a chunked ticket (about 6 transactions at N<=8, so the amplification there is about 6:1 and honest users can finish and bundle quickly, but occupancy is still possible). The pilot assumes N=100.
- Impact: no fund loss. Withdrawals and Series A funding are delayed for as long as the attacker pays roughly a tx fee plus priority fee per cycle, and keepers' fee-only wallet is drained at about 42x the attacker's spend (210,000 vs 5,000 lamports per cycle at N=100). Funds stay claimable (`claim_backer` and `open_position` are not blocked).
- Minimal fix (needs an economics decision; no schema/IDL/error change): route tolls below a threshold straight to seed, i.e. make `toll_route` return `TollRoute::Seed` when `toll < MIN_TICKET_TOLL` (a program constant; the Seed arm already exists, positions.rs:1318, and is conservation-neutral). Pick the threshold so a ticket's toll covers keeper cost, e.g. 1,000,000 lamports (about 0.001 SOL, roughly 4.7x the N=100 ticket cost at 5,000/signature). It changes who receives sub-threshold dust (seed instead of Backers). Operationally: clients should bundle `[commit_ticket, own payout]` whenever the ticket phase is `COMMIT`, and keepers should treat `COMMIT` as top priority.
- Required tests: (a) RED-today `positions_suite` row `dust_toll_routes_to_seed_without_a_ticket` using `World::genesis_with_simple_position_and_one_open_backer(gross)`, `warp_seconds` small, `withdraw_simple`; expect success, `PayoutPaid.ticket_id == 0`, `pool.active_ticket == 0`, `ticket().phase == IDLE`, `pool.seed` up by exactly the toll, `assert_vault_identity`. (b) boundary pair: toll = threshold-1 routes to Seed, toll = threshold routes to Ticket. (c) characterisation row in `fuzz.rs` adversary list (kind 15): bundled `[commit_ticket, withdraw_simple]` leaves a second honest payout at 6010, to record the cost ratio in `measure.rs`.

### SEC-4 (Low-Medium, deploy sequencing, confidence High): an unvalidated genesis provider tuple permanently disables the draw

- Location: `controls.rs:416-417` (`rng_authority.client = args.provider_client`, the only write ever), `close.rs:1081` (`require_keys_eq!(a.rng_authority.client, client.key(), WrongProviderTuple)`), `provider.rs:76-97` (`validate_client`, which already pins `client.key() == config.provider_client` and `== derived Client PDA`).
- Root cause: `initialize` stores the caller-supplied `provider_client` in an account no instruction can change, and every `request_round_draw` demands it equal the derived ORAO Client address. A typo, a zero tuple, or a client derived with a different program id/authority at genesis can never match. The same wrong value in `ConfigVersion#1` is fixable by staging v2; `RngAuthority` is not. Fail-closed: every close expires its promotion (`DeadlineNotReached`/`ProviderFeeExceeded`/`WrongProviderTuple` on request, B promotion lost), and funds are safe, but the feature is dead until a program upgrade.
- Impact: irrecoverable operator error at the single most irreversible step (initialize through the Squads vault).
- Minimal fix: (A) validate in `initialize`: `provider_client == provider::client_address().0` and `provider_program == orao::id()` (`WrongProviderTuple`, 6029). The M3 fixtures use synthetic `key(0xE1..0xE4)` (harness `src/controls.rs:524-537`, `initialize_args`), so they must switch to the derived values. Or (B) delete the redundant check at close.rs:1081 (`validate_client` already pins the same key through `config.provider_client` and the derived address); the existing row `request_rejects_wrong_client_owner_...rng_authority_bound_elsewhere` (6029) would be retargeted to a config-mismatch variant. Or (C, no program change) a deploy runbook gate: before `initialize`, compute `Client::find_address(program_id, rng_authority_pda, orao_id)` offline, assert it equals `provider_client`, and after initialize read back `RngAuthority.client`, `ConfigVersion#1.provider_*` and compare.
- Required test (for A): `initialize_rejects_provider_client_that_is_not_the_derived_orao_client` in `controls.rs` M3 (6029, fee-only), plus the positive control with the derived tuple.

### SEC-5 (Low, confidence High): `withdraw_provider_return` skips the live Squads profile check

- Location: `close.rs:1477-1482` (`require_vault_signer` + `governance.key() == pool.governance`) vs `controls.rs:598-606` (`require_governance` = `validate_profile` + `require_vault_signer`) used by `stage_config_version`, `rotate_recipient`, `rotate_guardian`, and `initialize`.

### SEC-7 (Info) = M9-F1 assessment: `claim_backer` has no deliverability preflight. Verdict: ACCEPT and document

- Control: `claims.rs:74-134` validates the destination with `validate_destination` and the protected list (claims.rs:97-102), takes `funded` (`mem::take`, claims.rs:60-63), debits `funded_claims`, then `send_game`. Nothing checks the Agave rent-state rule (post-balance of a data-less account must reach the 890,880-lamport minimum when credited).
- Why it is acceptable here but M8-F1 is not a precedent for ignoring it: the destination is chosen and signed by the Backer owner in the same transaction; a refusal is a runtime error at transaction end, which reverts every account write including the `funded` take (no loss, no double-claim, state unchanged, credit remains claimable). Unlike `close_shared_account`/owner-refund delivery there is no immutable third-party destination and no cash-progress dependency, so no one else can be blocked. A dust claim (1-10 lamports, measured 28,099 CU) simply needs a destination that already holds at least `min - amount`.
- Residual: clients must preflight `credit_is_deliverable(dest.lamports, amount, rent(0))` and say so; local LiteSVM cannot observe the refusal (pinned in `tests/transfer_constraints.rs`, which proves the predicate matches the Agave rule text but not local execution).
- Test status: no negative claim rows exist; see T1.

## Residual risks (reachable but accepted, bounded, or outside the program)

1. Surplus Free-funded Candidate pages for the in-progress close (`controls.rs:901-904`: `PageKind::Candidate { .. } => true` once `close_id` is not the next close). Any signer can spend sponsor `free_balance` on sequential Candidate pages beyond `required_pages_per_set` while a close is open. Spec-allowed and tested as intended (`provision_locked_close_rejects_index_at_or_beyond_required_pages_per_set.same_index_free` and `fallback_same_index_free` succeed). Funds return to `free_balance` through `close_shared_account` once the promotion is terminal, but the sponsor cannot withdraw them meanwhile and Free provisioning is starved for the window; cleanup is one page per instruction. If the spec owner wants it closed: bound the arm to `index < close.required_pages_per_set` (`WrongIndex`, existing code) and flip those two test rows.
2. Close-time terms come from the closing position's pinned config, not the pool's active one (`positions.rs:1274-1281,1340-1350`; `RequestRoundDraw`/`ApplyPromotion` read `close_record.config_version`). After a mid-round activation, whoever crosses the insolvency threshold with an old-version position chooses the provider fee schedule/tuple for that close. Bounded by what G staged; a bad old tuple fails closed (promotion expires).
3. B-promotion success depends on keeper throughput against the fixed 600 s window (`PROMOTION_DEADLINE_SECS`, `state.rs:34`). The closing ticket must commit before `build_candidates` is allowed (`close.rs:1018`); at N=100 the whole close is about 80 transactions. Sybil participants (each costs the participant about 0.0074 SOL of permanent rent plus the 4% load) inflate both the candidate-page reserve (2 x ceil(M/8) pages at about 0.0032 SOL) and build transactions; at a few thousand participants the promotion cannot finish in time and expires. Fail-closed; funds safe.
4. No emergency stop for outflows. `set_pause` gates only `open_position`/`fund_series_a` (`positions.rs:459,476`). A live exploit in payout/claim/management paths can be stopped only by a G program upgrade (48 h Squads delay). Decide before launch whether that is acceptable (an `Admission` flag change would alter a frozen SPACE).
5. Trust in ORAO and in the G vault: `cpi_withdraw` passes the G vault as a signer into the ORAO program (`provider.rs:202-211`), so an ORAO upgrade could act with the vault's signature for that CPI; G holds the program upgrade authority (`controls.rs:1448-1464`). Both are inherent to the design; call them out in the trust model.
6. DR-27 rent schedule: `sync_game` (`lib.rs:50-63`) and `sync_ops` (`86-96`) use the live `Rent::get()` floor and fail with `InvalidState` if the account balance falls below it; `ReserveSchedule` is captured at close but `create_locked_account` uses the live rate. Rent decreases (planned) only add surplus; an increase would underfund a captured reserve and could strand a captured draw (`expire_promotion` refuses a captured draw, `close.rs:1412`). No increase is expected.
7. `RngAuthority`-style one-write fields and the absence of any migration/realloc instruction: any future state-schema change needs a new migration instruction in an upgrade (frozen SPACE).
8. Operator runbook items the program cannot enforce: the ORAO Client must be registered with owner = G vault and state = the RngAuthority PDA before the first possible close; `provider_*` fields in config can drift from ORAO's live NetworkState (a staged tuple is not validated at stage time, only at request time).
9. `fund_series_a` reads the ACTIVE config (min_a, public flag) without an `expected_config` argument (frozen ABI); a funder can be subject to a flag/minimum change between signing and landing. Only the minimum and the flag are affected.
10. `unallocated_excess` (Ops) and `Pool.excess` are never spendable (no sweep path in the first release); mistaken transfers are stranded by design.
11. `increase_provider_budget` is permissionless by DR-33 (`close.rs:1445-1455`): a stranger can lock any amount of sponsor `free_balance` into the close partition and raise `approved_provider_fee_cap` before the request. Returned at settlement; spending is limited to the actual ORAO fee and rent. Accepted.
12. `request_round_draw` pre-funded request PDA fails closed (M7-F1, context only).
13. No event for `rotate_recipient` or `rotate_guardian` (monitors must diff accounts). `FundSeriesA.admission` is declared `mut` though never written (`positions.rs:249-254`), an unnecessary write lock on a hot account; changing it alters the frozen IDL.
14. Governance transactions travel through the Squads vault-transaction wrapper; their packet size/CU (initialize creates seven PDAs and parses two multisigs) are not measured here (M14).

## Non-findings (checked, fine, with the line that carries it)

- Every lamport out of GameVault is `send_game` (rent floor check `lib.rs:78`, vault key/owner `74-75`, destination validation `73`, no self-transfer `76`): `claims.rs:122`, `controls.rs:577`, `positions.rs:1310`. `grep` over production code finds no other `try_borrow_mut_lamports` except `close_shared_account` (`controls.rs:1257-1260`) and `send_game`.
- `close_shared_account` conserves lamports exactly: `page_lamports = ops + owner + remainder` (`controls.rs:1177-1181`), page zeroed, data zeroed, resized, re-assigned to system (`1257-1264`); a revived closed page is fresh but can never be re-provisioned because counters do not decrement (R3) and `AlreadyClosed` (6034) guards a second close.

- Candidate sets cannot be altered between seal and apply: `build_candidates` rejects after `sealed` (`close.rs:1019`), candidate pages close only after a non-Pending promotion (`controls.rs:1165-1169`) and cannot be re-created (counters).

- A captured draw is always applicable: `registry_extension_required` holds back the page rent exactly in the one case that needs a new registry page (new page needed only when `registry_len == 8 * registry_pages`, which implies `registry_len % 8 == 0` at the close because pruning only shrinks), and B-account rent is always held back (`close.rs:157-161`, `1287-1334`). No hostile input can make `apply_promotion` fail after a timely capture.
- Squads parsing is bounds-checked (`controls.rs:1474-1515`), the loop runs only after `member_len == 3` (`1376`), and the unwraps in `validate_program_binding` (`1441,1445,1460,1462`) follow explicit length checks (`1439`, `1457`).
- `initialize` cannot be front-run: it needs the G vault as a signer from a validated 2-of-3/48 h multisig (`controls.rs:300-316`) and the program's upgrade authority must already be that vault (`1428-1465`).
- Inline allocation: layout checked before any cash moves (`positions.rs:1252-1256`), exact count (`allocation.rs:1120`), no duplicates (`1121-1126`), writable (`1127`), identities proven by the same `discover_batch`/`allocate_batch`/`retire_row` code; fixed accounts and remaining accounts cannot alias because the types differ (Backer/RegistryPage/SnapshotPage vs Pool/Ticket/Position) and `destination` must be system-owned.

- No `unsafe` (`lib.rs:2` `forbid(unsafe_code)`); no reachable `unwrap`/`expect`/`panic!` outside length-checked slices.
