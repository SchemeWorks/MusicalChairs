## D8: authority and change policy

| Role / setting | Recommended default | Boundary |
| --- | --- | --- |
| Governance G | Autonomous Squads v4, 2-of-3, 172,800-second (48-hour) timelock | G Vault PDA owns loader upgrade authority, native configuration, provider client and management-recipient rotation. Three independently controlled voters are a launch input, not assumed current identities |
| Squad configuration | Zero-Pubkey `config_authority` sentinel; no spending-limit authority path | SDK null must serialize correctly. Verify config/vault transaction delays, threshold/settings changes, no alternate upgrade authority or bypass |
| Admission guardian P | Separate 2-of-3 multisig, zero delay; set/clear admission pause only | No writable financial/round/ticket/provider accounts in pause instruction. Guardian rotation belongs to G; losing guardian quorum may delay admissions until G rotates it |
| Management | Stored recipient signs; payout to that recorded recipient only | Withdraw only accrued Front-End Load. G-delayed recipient rotation; no pot/seed/claim/operations sweep |
| Progress | Any payer, no original keeper privilege | Public cash progress, result capture, deadline expiry, finalization and seed carry remain available under pause |
| Initialization | One authenticated initialization, bound to intended ProgramData upgrade authority and complete genesis config | No first-caller admin enrollment; no production test credit, backdate, manual winner, arbitrary balance or force-reset ABI |
| Schedule changes | Stage a version with `effective_round_id` no earlier than next round; activate only against expected Active round/config | Position pins terms; ticket pins economics; close pins deadline, candidates and provider tuple. Admission controls are immediate; future schedule cannot rewrite accepted liabilities |
| Provider changes | Future rounds only; stored close tuple remains immutable | Request checks registered client owner/state/config. No active rebind, second provider, alternate seed or callback-selected candidate |
| Repair | Admission pause, diagnose preserved state, reviewed upgrade/migration via G | No timeout deletes cash; upgrade delay remains in force, with no emergency single-key bypass. Funded claims/progress stay available to the extent the defect permits |

The [Solana deployment reference](https://solana.com/docs/programs/deploying) establishes that loader authority can replace code; [Squads timelocks](https://docs.squads.so/main/development/reference/time-locks) delay execution after approval. The delay holds while the configured Squad settings and Vault ownership remain intact, **not as an immutable loader guarantee**. A governance quorum can eventually change its settings or upgrade arbitrary code. Test the pinned Squads deployment's [configuration execution delay](https://github.com/Squads-Protocol/v4/blob/main/programs/squads_multisig_program/src/instructions/config_transaction_execute.rs), including reducing its own timelock. Same-G provider client ownership also permits callback changes/client-fund withdrawal under provider rules; this does not confer native balance authority and may force promotion omission. Renouncing upgrades, custom timelock wrappers, more signers and separate config/upgrade Squads are optional later choices.

## D6/D7/D9: processing, funding and availability

| Choice | Recommended default | Consequence / later proof |
| --- | --- | --- |
| Processing | Complete inline path when measured feasible; otherwise captured cursor work and one-row fallback | Keep `U_alloc(N)=3N+C_alloc+P_alloc(N)` work units. Closing adds participant/page phases and at most 64 sample counters; constants/page costs are measured, not fabricated |
| Keeper reward | **Zero on-chain reward in first release** | Two sponsor-run processes pay their own network fees. Any other payer can progress. Paid per-unit rewards are optional future work, requiring measurement and prospective policy; no claimant subsidy is assumed |
| On-chain reserve | Storage/page rent + provider request fee/rent cap + one possible automatic B account + fixed program-owned close costs | Must be segregated and available before payout/close mutation; accepted reserve cannot be withdrawn. Work-unit capture remains required even with reward price zero |
| Owner contribution | Optional explicit quote; `max_work_contribution_lamports=0` by default | May cover reserved storage/provider costs only if owner opts in. Insufficient reserve rejects before payout/state mutation; no silent haircut or retroactive charge |
| Funding/refund | Separate operations vault; free sponsor and per-ticket locked sponsor/caller partitions | Sponsor consumed first; caller covers quoted shortfall. Unused sponsor returns to free operations balance; unused caller amount returns to recorded owner. Provider-spent costs are not refundable game fees |
| Personal account rent | Owner pays User, Position, UserRound and self-funded A | Recorded payer/refund destination. Lifetime/EEC records persist; do not advertise immediate refund of permanent User/Backer rent |
| Automatic B rent | Sponsor pays from close reserve; winner need not sign or be online | Create/merge selected B permissionlessly; reserve possible account/page cost before closing payout. B lifetime record may persist indefinitely |
| Shared account rent | Sponsor pays config, vaults, registries, ticket/snapshot/candidate pages and provider client | Minimum excluded from game accounting; reclaim temporary pages only after financial/round obligations complete; abandoned candidate cleanup does not block reset |
| Pool bootstrap | Initial pot and seed **zero**, separate from protected rent and operations | Positive bootstrap is optional external launch funding with a named mechanism/receipt, never an assumed legacy transfer or hidden management subsidy |
| Round oracle policy | One immutable close+600 Clock seconds; timely capture <= deadline, expiry > deadline; no reroll | Canonical `PromotionApplied` / `PromotionSkipped(reason)` with Deadline, NoCandidates or EntropyExhausted. Cash commit precedes full seed carry once; no ten-minute wall-clock guarantee |
| Provider adapter | ORAO registered-client interface first, direct authenticated result capture as baseline | No mutable client-level callback required. Pin tuple/seed/marker; require direct read/retention tests. Capture-only request-level callback is optional if useful and proven, never financial allocation in callback |
| Keepers/alerts | Two independent process failure domains; same public permissions; 60s no-progress alert, 300s escalation | No lease or admin resume credential. If both stop, any wallet can prepare a valid one-row/capture/expire/finalize transaction |
| Benchmarks | Inline N=0/1/16/17; allocations/participants 64/256/1,024; row chunks 1/4/8; churn, dust and outages | Test cases, not a cap or supported capacity. Measure CU/account/transaction size, rent/cost, latency tails and sponsor depletion; return a concrete redesign if infeasible |

At zero reward price, the on-chain reserve **does not include prepaid keeper network fees**. Those are an external sponsor operating budget or a self-funded caller expense. Failure of that operating budget cannot disable the progress instruction, but there is no promise that someone will submit transactions. Pending claims/tolls remain protected. Tiny valid withdrawals may exhaust sponsored storage and serialize cash processing; no new minimum, cooldown or population cap is silently added. Provider authentication/lifecycle proof is an implementation obligation for the selected adapter, not an optional proof to postpone until after launch.

**Operations funding/authority contract:** `fund_operations(amount)` accepts any signing sender's explicit non-refundable sponsor contribution, recorded as free sponsor balance with no Position, PP reward, Backer entitlement, quota use or donor-withdrawal right. The configured sponsor-recipient signer alone may `withdraw_unreserved_operations(amount)` to itself, bounded by free accounted balance after protected vault rent and every accepted reserve; G rotates this recipient prospectively under its delay. Anonymous plain transfers remain unallocated excess, not free balance. Top-ups do not create an unbounded donor-refund registry.

At reserve admission move exact amounts from free sponsor balance and opted-in owner into `locked_sponsor` / `locked_owner` fields of the ticket/close, with immutable owner refund destination. These locked partitions cannot be withdrawn by sponsor, G configuration or another ticket. Consume the sponsor partition first using the captured cost schedule, then the owner partition only within quoted maximum. Refund unused sponsor to the operations vault's free balance and unused owner to recorded owner exactly once after required work/cleanup. Funds already spent on provider fees are consumed. Persistent storage is a distinct outstanding cost: record each account's beneficial rent funding in at most two fixed components (operations vault and opted-in owner), and return those components only on proven safe closure, never prematurely in terminal ticket refund. Actual Solana rent payer may be the vault PDA; it is not the same as beneficial contribution/refund identity. Test source consumption, account-rent partitions, no double refund and physical operations-vault equality through every phase.

**Signer/payer contract:** owner wallet remains financial authority and gross deposit source regardless of transaction fee payer. Personal User/Position/UserRound/A creation enforces owner as instruction rent payer in first release; automatic B/shared storage uses reserved operations-vault funds, with the above fixed refund components if owner opted into shortfall. Third-party transaction fee sponsorship is permitted by the protocol and does not authorize deposits from another owner, change payout destinations or alter rent refund ownership. GUI defaults its fee payer to owner. A rent-sponsorship service or different personal-rent payer is optional later interface work, not implicit in third-party network-fee payment.

Source references: `shenanigans/main.mo:1400–1487,1558–1590,1595–1660`; wallet/CSP `frontend/src/lib/siwsSigner.ts:158–237`, `hooks/useWallet.tsx:376`, `solana/sendSolDeposit.ts:96–103`, `frontend/public/.ic-assets.json:19`.

The program is callable by other clients: a third party may submit v1 even when this GUI sends v0. Account-state reads remain usable; history/reward ingestion must decode those observed transactions through a supported raw-RPC adapter and matching `maxSupportedTransactionVersion`, independently of frontend signing libraries. Test that an external newer-format call cannot lose a PP entitlement or advance the cursor past a gap. This parser obligation is part of preserving history/rewards, not a frontend SDK migration.

Native PP ingestion uses a write-ahead durable outbox. Persist validated basis/policy and pending beneficiary pubkey even without SIWS; once bound, calculate and reserve the player's effects/cascade/siphon obligations exactly once before any ledger await. Each leg stores immutable recipient, amount, fee, 32-byte domain-separated event/leg memo hash and `created_at_time`, with Pending/SubmittedUnknown/Committed/Retryable/Quarantined status. Retries repeat identical transfer fields within the verified ledger dedup window; `Duplicate` reconciles to the prior receipt. Unknown outcome after that window requires ledger-history reconciliation, never a fresh timestamp and blind remint. If receipt cannot be established, keep the leg quarantined for proof-bearing recovery. Cursor may advance over durable outbox storage, not a missing range; completed legs never repeat when another leg fails. Native ingestion cannot blindly reuse `mintInternal`, which currently chooses a new timestamp per call (`shenanigans/main.mo:2015–2030`), or the documented commit/write gap in `mintWithEffects` (`:2871–2924`). Prove the actual PP ledger's memo limit, dedup/history interface and receipt recovery during integration; no generic ICRC assumption establishes exactly-once minting.

## What remains for implementation and launch

**Implementation proofs:** accepted integer oracle/vectors; complete allocation and round state; measured resource costs; exact locked provider/toolchain compatibility; signer/account/authority/replay constraints; rent/refund/conservation; bridge gaps/partial mint/rebinding protection; existing GUI and direct canonical reads. No SVM/build/devnet/production proof exists yet. These checks belong in the scoped implementation sequence, not extra preparatory projects.

**Launch-only inputs:** actual independent governance/guardian voters and Vaults, management recipient/sponsor, production cluster/program/provider identity and configured RPC/archive/CSP/SIWS origins, operations operating budget and optional bootstrap capital, tested performance envelope and release/funding authorization. Default zero bootstrap does not mean zero deployment/rent/operations expense. Verify deployed legacy withdrawal/settlement/claim/desk capabilities separately; no legacy pause/shutdown is implied.

**Deferred optional work:** native PP/desk, account merging/rebinding, refund attribution for plain SOL transfers, paid on-chain keeper incentives, v1/Kit migration, Pinocchio/alternative allocation optimization, custom timelock or immutable deployment, more governance signers. None is presented as a prerequisite to implement this chosen first-release scope.
