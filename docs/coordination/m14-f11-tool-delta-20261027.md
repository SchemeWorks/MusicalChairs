## F11-R1 correction (Gideon's blocking finding on `5aa64e1`), fixed in `1765c2f`

**Finding.** `cmd_execute_tl` checked profile, action, status and time, but never re-scanned the other G transactions:
- A G transaction created during the 48 h wait, or a hand-made config, would be staled by the config execute.
- The real binary shows an already-Approved stale vault transaction still executes.
- The old test at `g_timelock.rs:1429-1455` even executed through the guarded CLI while earlier Active and Approved vault proposals were live.
- A manual `status` check is not an enforced guard.

**Fix.** `timelock.rs` (+118 lines). A new `require_no_other_live` is called in `cmd_execute_tl` after `load_checked_config` and `require_not_stale`. It runs BEFORE the status and time-lock checks and `run_step`, so in both dry runs and `--execute`, a refusal precedes any signing, signed simulation or send. It enforces two rules:
- **Exact index:** the executing index must equal G's latest `transaction_index` (R4 and S3).
- **Full bounded scan of `(stale, transaction_index]`:** every other index must be Executed, Rejected or Cancelled. The only exclusion is the executing config, already proven exactly `[SetTimeLock{target}]`.
  - Refused: a live proposal; an orphan (no exception for an identical config); a missing, unrecognized or undecodable account; a read error; a range above `LIVE_SCAN_CAP`.

The receipt gains `other_g_transactions_checked`. F3, pending/history, the current-lock deadline, `run_step` and `devnet_ops.rs` are unchanged.

**Tests.** `g_timelock.rs` (+321 / −17 lines):
- **Three new tests:**
  - `execute_refuses_when_a_foreign_transaction_appears_after_the_approval_for_reduce_and_restore`: a foreign Active vault proposal, an Approved one, an orphan vault transaction and an orphan identical config, each created AFTER the intended approval, in both directions.
  - `execute_refuses_a_live_or_orphan_foreign_transaction_below_the_executing_config_for_reduce_and_restore`: proves the scan beyond the index rule, with a positive control. Once the foreign Approved transaction has really executed, the execute passes and the receipt lists it.
  - `execute_refuses_a_range_above_the_scan_cap_instead_of_scanning_part_of_it`.
- **Every refusal is asserted in BOTH dry run and `--execute`:** the exact reason; ZERO signed or unsigned simulations and sends; the pending file byte-identical; the time lock, stale index and transaction index unchanged; the intended proposal still Approved.
- **The raw-Squads stale experiment** now executes its deliberately unsafe config directly through the fixture (a raw `config_transaction_execute_ix`, not the CLI). The same finding is recorded: stale index 5, a stale Active vote 6007, an approved-then-stale vault transaction executes. The guarded CLI is asserted to refuse that state.
